# 企业知识库智能问答后端

上传企业文档，用自然语言提问，**答案只来自你的文档，并标注出处**。

和普通聊天机器人的区别在这里：大模型用的是训练时记住的知识，答不出你公司的报销流程，问急了还会编。
这个系统把文档切分、索引、检索之后，只把检索到的片段交给模型，并要求它标注引用编号——
每一句结论都能点回原文核查。

## 效果实测

以下数字都是在本机真实跑出来的，不是估算。

| 指标 | 实测值 | 怎么测的 |
| --- | --- | --- |
| 首字延迟 | **801 ms** | 从发出提问到界面吐出第一个字（流式返回） |
| 整段回答耗时 | 约 1.5 s | 同一问题的完整生成时间 |
| 检索命中率 | **100%** | 12 道题（8 道可回答）的评测集，见下文 |
| 单次提问成本 | 约 **0.0018 元** | 输入 387 + 输出 126 token，按配置单价计算 |
| 自动降级 | 主模型故障时 **1 次请求内切备用** | 把主模型地址改成不通的端口实测 |

## 快速开始

前置条件：JDK 17，以及一个模型 API 密钥（当前默认接 DeepSeek）。

```powershell
# 1. 构建
.\mvnw.cmd -DskipTests package

# 2. 把密钥写进 .env.local（该文件已被 git 忽略，不会提交）
#    DEEPSEEK_API_KEY=sk-xxxxxxxx

# 3. 启动（一个窗口，保持开着）
.\tools\run-local.ps1
```

另开一个窗口，把样例文档喂进去，然后提问：

```powershell
.\tools\upload-doc.ps1 .\samples\产品需求说明.md
.\tools\ask.ps1 "系统对首字延迟的要求是多少"
.\tools\ask.ps1 "那成本怎么控制" -Session demo      # 同一会话的追问
.\tools\ask.ps1 "什么是混合检索" -Stream            # 观察流式输出

.\tools\search.ps1 "分块策略" -Mode hybrid          # 只做检索，不走模型
.\tools\stop-local.ps1                              # 停止
```

## 一次提问经过什么

```
上传 → 解析(PDF/Markdown/TXT) → 分块 → 向量化 → Lucene 索引
                                                    │
提问 → 相关性门控 → 双路召回(BM25 + 向量) → RRF 融合 → 组装提示词 → 流式生成 → 引用来源
```

- **解析**：PDF 逐页提取并保留页码，Markdown 记录标题路径；编码自动识别 UTF-8 / GB18030 / BOM。
- **分块**：结构优先——标题行归位、段落边界不跨越、句子边界累加、块间保留重叠，每块带来源定位。
- **召回**：关键词与向量两路并行，各取一份排序名单。
- **融合**：RRF，只看名次不看分数（两路分数量纲不同，直接加权需要归一化和调参）。
- **生成**：提示词硬性要求只依据资料作答、没有依据就直说、引用要标编号。
- **降级**：主模型失败自动切备用；流式调用只在还没吐出第一个字时允许切换。
- **计量**：每次调用记录 token 与成本，失败的也记。

## 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/documents` | 上传文档（multipart，字段 `file`），返回后后台解析 |
| GET | `/api/documents/{id}/chunks` | 查看切分结果，用来检查分块质量 |
| POST | `/api/chat` | 提问，一次性返回答案与引用 |
| POST | `/api/chat/stream` | 提问，SSE 流式返回：`citations` → `delta` → `completed` |
| GET | `/api/search?q=&mode=` | 只检索不生成，mode 可选 keyword / vector / hybrid |
| POST | `/api/search/reindex` | 重建索引（换向量模型后必调） |
| GET | `/api/usage/summary` | 用量与成本汇总，按模型拆分 |
| POST | `/api/eval/run` | 跑检索评测，返回命中率、MRR 等指标 |

## 检索评测：混合一定更好吗

评测集在 `src/main/resources/eval/questions.json`：12 道题，其中 8 道可回答、4 道知识库里没有答案。
跑法：`POST /api/eval/run?topK=5`（只做检索，不调用大模型，所以反复跑不花钱）。

| 模式 | 命中率 | MRR | 平均耗时 | 可回答问题首条分 | 不可回答问题首条分 |
| --- | --- | --- | --- | --- | --- |
| keyword | 100.0% | 0.938 | 6.4 ms | 4.68 | 1.00 |
| vector | 87.5% | 0.729 | 1.3 ms | 0.63 | 0.61 |
| hybrid | 100.0% | 0.938 | 1.8 ms | 0.033 | 0.028 |

**结论一：在这个评测集上，混合并没有比关键词更好。** 原因是我的题目措辞和文档用词高度重合，
对关键词检索天然有利。评测集的偏差本身就是个教训——题目该怎么写，和指标一样重要。

**结论二：融合分数不能用来判断相关性。** 看最后两列：关键词的可回答问题 4.68 分、
不可回答 1.00 分，区分度明显；而 RRF 融合后两者几乎一样（0.033 vs 0.028）。
原因是 RRF 只看名次，排第一的片段无论相不相关都拿同样的分——这是它的结构决定的。

**结论三（由结论二直接得出）**：相关性门控必须基于 BM25 分数，不能基于融合分数。
实现见 `chat/RelevanceGate.java`：最高 BM25 分数低于阈值时，直接当作"没有找到依据"，
**不调用模型**。实测拦截一个不相关问题耗时 138 ms，且模型调用次数没有增加。

阈值默认关闭（`app.chat.min-keyword-score: 0`）。原因很实在：12 道自造题目标出来的数字
不足以当线上默认值，语料规模和用词分布一变化就要重新标定。机制做好、方法留清楚，
比拍一个好看的数字负责。

## 技术选型

| 选择 | 理由 |
| --- | --- |
| Spring Boot 3.5 + Java 17 | 国内主流版本，资料与生态兼容性明确 |
| WebFlux + SSE | 流式返回的原生方案；响应式链路上还顺便暴露了 MDC 传递的坑 |
| 内嵌 Lucene | 一个引擎同时提供 BM25 全文检索与 HNSW 向量检索，零外部服务 |
| CJK 二元分词 | Lucene 自带，明显优于标准分词器的逐字切分；生产环境可换 IK 或 jieba |
| H2 文件库 + JPA | 免安装即可跑通；换 PostgreSQL 基本只改连接串 |
| 手写 OpenAI 兼容客户端 | 不依赖厂商 SDK，换一家只改 base-url；SSE 增量解析自己实现 |

## 部署须知

构建产物是一个可独立运行的 jar，`java -jar` 即可启动。要放到服务器上长期跑，还需要注意三件事：

1. **密钥**：通过环境变量注入（`DEEPSEEK_API_KEY`），不要写进配置文件或镜像；
2. **数据**：`./data` 下是 H2 数据库、上传的原始文件和检索索引，必须挂载到持久化磁盘，
   否则重启就丢；正式环境建议把数据库换成 PostgreSQL（改连接串即可）；
3. **入口**：服务只监听 HTTP，不代表可以直接暴露到公网；评测接口 `/api/eval/run` 应当鉴权或关闭。

本机没有安装 Docker，所以没有随仓库提供容器化配置——与其提交一份没验证过的 Dockerfile，
不如把上面三条讲清楚。

## 已知不足

主动写出来，是因为说不清自己系统边界的人，通常也没真正做过。

| 不足 | 影响 | 该怎么补 |
| --- | --- | --- |
| 向量用的是本地兜底实现（字符 n-gram 哈希） | 关键词那一路真实可用，语义那一路只是链路跑通 | 配一个真实向量模型（如 bge-m3），改配置后调 `/api/search/reindex` |
| 评测集只有 12 道题且措辞偏向关键词 | 结论只能说明趋势，不能当基准 | 扩充题目并加入改述问法 |
| 会话存在单机内存 | 重启丢失、多实例不共享 | 挪到 Redis |
| 解析期间占用数据库事务 | 文档量大时连接会紧张 | 拆成"置为解析中 / 解析切分 / 写入结果"三段短事务 |
| 没有熔断 | 某个模型持续故障时每次都要先失败一次 | 引入 Resilience4j 做失败窗口统计 |
| 追踪号只在阻塞段可见 | 事件循环线程上的日志仍显示占位符 | 接入 Micrometer Tracing 或 OpenTelemetry |
| 没有权限体系、没有前端 | 只能本地或内网使用 | 第一版明确不做，见 `docs/scope.md` |

## 目录结构

```
src/main/java/com/example/rag/
├── document/   文档上传、解析、分块（含编码识别与四种解析器）
├── embedding/  向量化：可切换提供方 + 本地兜底实现
├── retrieval/  Lucene 索引、双路召回、RRF 融合
├── chat/       问答编排、提示词组装、会话上下文、相关性门控
├── llm/        模型客户端、流式解析、多提供方路由与降级
├── usage/      用量与成本计量
├── eval/       检索评测执行器
└── support/    阻塞调用的线程隔离、追踪号

docs/scope.md      范围说明、决策记录、踩坑记录
docs/walkthrough.md 大白话讲解：这个系统在干什么
samples/           演示用文档
tools/             启动、上传、检索、提问等辅助脚本
```
