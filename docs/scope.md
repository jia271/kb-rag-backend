# 项目二 · 企业知识库智能问答后端 —— 范围说明书 v0.1

> 这份文档是"第一步"的产物：在写代码之前先把边界锁死。
> 后面每加一个功能，都先问一句"它在不在这一页纸里"，不在就不做。

## 1. 一句话定位

把企业内部的 PDF / Word / Markdown 文档变成可检索的知识库，对外提供**带引用来源的流式问答 API**，
并具备多模型路由、自动降级、token 计量与调用链路追踪等生产级能力。

## 2. 这个项目要证明的四件事（面试主轴）

| 主轴 | 对应面试考点 |
| --- | --- |
| 检索增强链路的工程实现与可度量优化 | RAG 原理、分块策略、混合检索、召回率怎么调 |
| 流式与异步并发 | WebFlux、SSE、长任务异步化、超时与断连处理 |
| 稳定性与成本控制 | 多模型路由、降级重试、token 计量、链路追踪 |
| 效果可量化 | 自建评测集、TTFT、召回率、单次成本对比 |

## 3. MVP 范围（做完这些就算第一版可演示）

功能：

- 上传文档（PDF / Markdown / TXT）→ 异步解析 → 切分 → 向量化入库
- 提问 → 流式返回答案 + 引用来源（文件名 + 片段 + 页码/段落号）
- 多轮会话上下文管理
- 会话与文档的列表/删除接口

非功能：

- 单接口 200 并发下不报错
- 有健康检查、结构化日志、异常统一返回

### 验收标准（可逐条执行的检查项）

1. 上传 20 份文档（合计约 200 页），10 分钟内完成索引
2. 提 10 个问题，答案正确，且引用指向真实文档片段
3. 本地环境首字延迟（TTFT）< 1.5s
4. 服务重启后索引与会话数据不丢

## 4. 明确不做（第一版）

- 不做完整前端（用 curl 或一个单页 HTML 演示即可）
- 不做登录、权限、多租户
- 不做微服务拆分
- 不做分布式向量数据库（见 5.2 决策）

### 5.2 检索与向量存储（关键决策）

本机没有 Docker，pgvector / Milvus 需要容器环境，安装成本高。
第一版推荐 **内嵌 Apache Lucene**：

- 同一个引擎里既有 BM25 全文检索，也有 HNSW 向量检索，天然支持混合检索
- 零外部依赖，纯 Java，本地直接跑，面试演示不用现场起服务
- 故事更好讲："先用内嵌 Lucene 实现混合检索，后期因 X 原因迁移到 pgvector/Milvus" —— 有取舍才有深度

后期（可选）：迁移到 PostgreSQL + pgvector，或 Milvus，并把迁移原因与压测对比写进 README。

### 5.3 模型接入

- 抽象 `ModelProvider` 接口，支持 OpenAI 兼容协议，便于接多家
- 通过配置切换主备模型，为"路由 + 降级"打底
- 主模型：DeepSeek（`deepseek-chat`），密钥通过环境变量 `DEEPSEEK_API_KEY` 注入，不写进仓库
- **不引入 Spring AI**：少一层抽象、无版本兼容风险，而且手写 SSE 增量解析本身就是这个项目的亮点之一

## 11. 踩坑记录（环境相关，M1 会再遇到）

### Windows PowerShell 5.1 读取「UTF-8 无 BOM」文件会出错

现象：`tools\run-local.ps1` 报「字符串缺少终止符」，脚本根本无法解析；改成纯英文后脚本能跑了，
但密钥依然读不到，而且没有任何报错。

原因：Windows PowerShell 5.1 默认按系统 ANSI 编码（中文 Windows 即 GBK）解码文件，
而 PowerShell 7 默认按 UTF-8。同一份文件，7 读到 140 个字符 / 3 行，5.1 只读到 158 个字符 / 1 行——
多字节序列被打乱，连换行符都被吞掉，整份文件变成一行注释，配置项自然匹配不到。

对策：

1. `.ps1` 脚本内容保持纯 ASCII，注释也一样；
2. 读取配置统一走 `[System.IO.File]::ReadAllText($path, [System.Text.Encoding]::UTF8)`；
3. 读不到任何配置时要显式报警，不允许静默失败。

延伸：M1 解析文档时一律显式指定字符集，不要依赖 JVM 或系统的默认编码。

### 同一个坑的第二种症状：注释里的中文会吞掉下一行代码

在 `tools/search.ps1` 里又踩了一次：脚本能通过语法检查，也能正常运行，但参数始终是空的。
原因是一行中文注释在 ANSI 解码后字节长度发生变化，把紧跟其后的那行代码一起吞进了注释里。

结论：`.ps1` 文件必须保持**纯 ASCII**，注释也一样。这条规则没有例外。

## 13. 分块策略（M1 的核心，面试重点）

目标是"结构优先、长度兜底"，具体规则：

1. **标题行先归位**：纯文本里短、单独成段、没有句末标点的行视为标题，并到下一段。
   不这么做的话会切出"只有六个字"的碎片，检索时毫无价值。
2. **段落边界不跨越**：先按空行切段落，一个块里混两个主题，检索出来就是噪音。
3. **段落内按句子边界累加**：在句号、问号、分号、换行之后切，凑到 `max-chars` 就出一块。
4. **块间保留重叠**：把上一块的尾部（`overlap-chars`）接到下一块开头，
   并尽量从句子边界开始，避免答案正好落在切分边界上。
5. **过短的尾块并回前一块**：放得下就并；放不下就单独成块——宁可留个小块，也不能丢内容。
6. **保留来源定位**：每个块记录来源页码（PDF）或标题路径（Markdown），回答时要标注出处。

三个可调参数都在 `app.chunking` 下：`max-chars`（默认 800）、
`overlap-chars`（默认 120）、`min-chars`（默认 120）。

实测：结构清晰的 Markdown 每个小节成一到两块，平均 60 字左右；纯文本长段落约 150–200 字一块。
**块偏小是结构优先的代价**，换来的是每个块主题单一、引用出处精确。
到底多大最合适，要等 M5 建好评测集才能用数据回答，现在先不要凭感觉调。

## 15. 检索策略（M2 的核心）

检索引擎用内嵌 Lucene：同一个索引里既有全文倒排（BM25），也有 HNSW 向量索引，不用额外起服务。

**两路召回各自有短板**，这正是混合检索存在的理由：

- 关键词检索擅长精确匹配（错误码、专有名词），但不懂同义词，问法和文档写法不一致就找不到；
- 向量检索懂语义，能处理换一种说法，但对精确字符串不敏感，也可能召回语义相近却实际无关的内容。

所以 hybrid 模式两路都跑，再用 RRF 融合：`分数 = Σ 1 / (k + 名次)`，k 默认 60。

**为什么用名次而不是原始分数**：BM25 分数和余弦相似度量纲完全不同，直接加权求和必须先归一化，
而归一化又要靠调参。RRF 只看"排第几"，天然免疫量纲问题，实现简单且效果稳定。

接口返回里保留 `keywordRank` 和 `vectorRank`，是为了让"这条为什么排在前面"可解释——
面试被追问排序依据时，这两个字段就是答案。

## 16. M2 决策记录

| 日期 | 决策 | 理由 |
| --- | --- | --- |
| 2026-10-14 | 检索用内嵌 Lucene，不引入独立向量库 | 本机没有 Docker；Lucene 同时提供 BM25 与 HNSW，零外部依赖 |
| 2026-10-14 | 融合用 RRF 而非加权求和 | 两路分数不可比，加权求和需要归一化与调参 |
| 2026-10-14 | 索引目录按「提供方-维度」分子目录 | 换模型时维度通常会变，新旧向量混在同一索引里会直接报错 |
| 2026-10-14 | 中文分词用 Lucene 自带的 CJK 二元切分 | 零额外依赖，明显优于标准分词器的逐字切分；生产环境应换成 IK 或 jieba |
| 2026-10-14 | 向量化提供方做成可切换接口 | DeepSeek 只有对话模型，没有 embedding 接口，必须能接别家 |
| 2026-10-14 | 索引在数据库事务之外执行 | 向量化要走外部接口，塞进事务会让事务持有连接的时间被网络延迟撑长 |
| 2026-10-14 | 索引失败不把文档标记为失败 | 文本已经入库，只是暂时搜不到；修好配置后调重建接口即可补齐 |

**当前效果的真实边界**：默认用的是本地兜底向量化（字符 n-gram 哈希），它只是把字面重叠多的文本
映射到相近的向量上，**没有语义理解能力**。混合检索里关键词那一半是真实可用的，
向量那一半现在只保证链路跑通。

要拿到真正的语义检索效果，需要接一个向量模型。推荐硅基流动的 `BAAI/bge-m3`（OpenAI 兼容，有免费额度）：

1. 在 `.env.local` 里加一行 `SILICONFLOW_API_KEY=你的密钥`；
2. 把 `application.yml` 里 `app.embedding.providers.siliconflow.enabled` 改成 `true`，
   并把 `default-provider` 改成 `siliconflow`；
3. 调一次 `POST /api/search/reindex` 重建索引。

## 17. 问答链路（M3 的核心）

流程：检索 top-K 片段 → 组装提示词 → 流式生成 → 标注引用来源。

**提示词规则**（写在 `RagPromptBuilder` 里，这几条直接决定答案质量）：

1. 只使用资料中的信息，不允许用模型自己的知识补充；
2. 资料里没有就直说"知识库中没有找到相关内容"，不要编造；
3. 引用要标编号 `[1]`、`[2]`，编号与接口返回的 `citations` 一一对应；
4. 用简体中文、条理清晰，不要复述全部资料。

**流式协议**：`POST /api/chat/stream` 返回 SSE，事件顺序固定：

- `citations`：先把引用来源推给前端，用户立刻看到依据；
- `delta`：逐段推送答案文本；
- `completed`：完整答案、首字延迟、总耗时、会话 id；
- `error`：出错时的兜底事件。

**实测结果**（真实调用 DeepSeek，不是模拟）：

- 首字延迟 801 ms、整段回答 1484 ms，满足 MVP 验收标准里的"首字延迟低于 1.5 秒"；
- 同一个会话里追问"那切得太小会有什么问题"，能正确承接上文；
- 问知识库里没有的内容，模型按规则回答"知识库中没有找到相关内容"，没有编造。

### 一个值得记录的发现：相关性问题拦截不住

问"公司年会在几月几号举办"，检索仍然返回了 3 条片段——BM25 只要匹配到任意一个词就会返回结果，
所以"检索不到就拒绝回答"这条兜底分支在真实场景里几乎不会被触发。

真正拦住它的，是提示词里的第 2 条规则。这说明**检索层返回"有结果"不等于结果相关**。
后续应该加相关性阈值门控（低于阈值的片段直接丢弃），但阈值必须用评测集标定，
所以这件事放到 M5 用数据来做——现在凭感觉设一个数字，只会引入新的不确定性。

## 18. M3 决策记录

| 日期 | 决策 | 理由 |
| --- | --- | --- |
| 2026-10-14 | 会话上下文放单机内存，不建表 | 先跑通链路；代价是重启即丢失、多实例不共享，正式做法应放 Redis |
