# 这个系统到底是什么（大白话版）

> 这份文档不写代码，只讲清楚三件事：它在干什么、每个部分为什么存在、你能不能三分钟讲给别人听。

## 一、一句话说清楚

它是一个**"问文档"的服务**。

你把公司资料丢进去 → 它把资料读进肚子 → 你用平常说话的方式提问 → 它从资料里找出相关的段落 →
交给大模型生成答案 → 并告诉你这句话出自**哪份文件的哪一段**。

关键点：**它不是普通的聊天机器人。**

普通聊天机器人用的是训练时记住的知识，答不出你公司的报销流程，问急了还会编。
这个系统的价值在于"**答案只来自你给它的资料**"，所以可以核查、可以追溯。

## 二、跟着一次提问走一遍

真实的例子：问「文档里说的分块策略是什么」。从你按下回车到看到答案，中间经过五站。

### 第 1 站：请求进来

你发一个 HTTP 请求到 `/api/chat`，里面装着你那句话。
服务收到后做一件小事：如果你没给会话号，就新建一个——这样后面的追问才能认出"你是谁、刚才聊了什么"。

> 对应代码：`chat/api/ChatController.java`

### 第 2 站：找资料（两个工人各自交一份名单）

这是整个系统最核心的一站。你的问题被同时交给两个"找资料的工人"：

- **工人 A 负责按字面找**：像 Ctrl+F，靠关键词匹配。它的长处是精确，比如查一个错误码、一个专有名词，一找一个准。短处是不懂同义词，你问"怎么防胡编"，文档里写的是"幻觉"，它就找不到。
- **工人 B 负责按意思找**：它把你的问题和每个片段都变成一串数字（叫"向量"），意思越接近，数字越接近。长处是能接受换个说法，短处是对精确字符串不敏感，还可能找出一堆"意思相近但实际无关"的内容。

两个工人各自交一份**按相关度排好序的名单**，然后合并。

合并的办法叫 **RRF**：不看两者的分数，只看各自的名次——第 1 名算 1/61 分，第 2 名算 1/62 分，最后加总。
为什么不用分数直接相加？因为这两个分数根本不是一回事（一个是 BM25 分，一个是余弦相似度），
量纲不同，硬加会出错，要做归一化又得调一堆参数。只看名次就没这个问题。

> 对应代码：`retrieval/ChunkIndexService.java`（两个工人）、`retrieval/HybridSearchService.java`（合并）、`retrieval/RrfFusion.java`（RRF 算法）

### 第 3 站：拼提示词

把找出来的段落编号成 [1]、[2]、[3]，连同几条硬规则一起交给大模型：

1. 只准用这些资料回答，不准用你自己的知识补充；
2. 资料里没有就说"知识库中没有找到相关内容"，不准编；
3. 引用要标编号 `[1]`；
4. 用简体中文，条理清晰。

**这几条规则是整个系统里性价比最高的代码。** 十几行字，决定了答案会不会胡编。

> 对应代码：`chat/RagPromptBuilder.java`

### 第 4 站：模型一个字一个字往外吐

大模型不是等整段写完才给你，而是一个词一个词地生成。
我们在收到第一个字时记下时间，收到一段就立刻推给前端一段。

这样用户不用干等——**我们的实测首字延迟是 801 毫秒**，而整段回答要 1484 毫秒。
如果等整段写完再返回，用户会觉得卡了 1.5 秒；现在他从 0.8 秒就开始看到字了。

> 对应代码：`llm/OpenAiCompatibleLlmClient.java`（流式解析）、`chat/ChatService.java`（编排）

### 第 5 站：把出处一起还给你

接口返回的 `citations` 里带着每一段的来源：文件名、页码或章节标题、原文片段。
答案里写的 `[1]` 就对应这份列表里的第 1 条。

**这就是"可核查"的含义**：用户能顺着编号点回原文，自己判断答案可不可信。

## 三、每个部件少了会怎样

这张表建议你背下来，面试时被问到"你为什么要做 XXX"就是这个思路。

| 部件 | 它解决什么问题 | 去掉它会发生什么 |
| --- | --- | --- |
| 编码判断 | 中文文档里混着 UTF-8、GBK、带 BOM 的文件 | 进系统的全是乱码，后面再优化都没用 |
| 文档解析 | 把 PDF/Markdown/TXT 变成纯文本 | 只能处理纯文本，PDF 一边儿玩去 |
| 分块 | 把长文档切成检索用的片段 | 整篇文档当一块，检索出来一半内容不相关 |
| 混合检索 | 关键词 + 语义两路找 | 只用一个：要么查不到换个说法的问题，要么匹配不准 |
| RRF 融合 | 把两份名单合成一份 | 两个分数没法直接比，排序就是错的 |
| 提示词约束 | 限制模型只说资料里的话 | 模型开始自由发挥，你无法判断真假 |
| 引用来源 | 让答案可追溯 | 用户没法验证，等于又信了一个黑盒 |
| 流式输出 | 让用户尽早看到内容 | 首字延迟从 0.8 秒变成 1.5 秒以上 |
| 会话上下文 | 记住前面聊了什么 | 追问"那它呢"时，系统不知道"它"指什么 |
| 结果缓存（未做） | 重复问题不必重复计算 | 同样的问题反复花钱调模型 |

## 四、你做的五次提交，各是什么

| 提交 | 一句话 |
| --- | --- |
| M0 | 把工程搭起来，确认能和 DeepSeek 说上话（这一步排除的是环境和密钥问题） |
| M1 | 文档进来：解析成文本、切成片段、存进数据库 |
| M2 | 能搜索了：关键词 + 向量两路召回并融合排序 |
| M3 | 能问答了：检索 + 提示词 + 流式生成 + 引用来源，形成完整闭环 |
| M4 | 扛得住了：主模型挂了自动切备用、每次调用记 token 和花费、请求带追踪号 |

| 补丁 | 几个方便自己用的命令行工具（上传、检索、提问） |

## 五、面试官会从哪里问进来

| 他可能问 | 你怎么答 |
| --- | --- |
| 这个项目解决什么问题？ | 企业内部文档散落在各个网盘和聊天记录里，新同事查一条规则要翻十几个文件。我做的是让文档可被提问，并且答案能追溯到原文。 |
| 和直接用 ChatGPT 有什么区别？ | ChatGPT 用的是训练时记住的知识，答不了公司内部文档，也不给你出处。我的系统答案只来自上传的资料，每句话都能点回原文核查。 |
| 为什么用混合检索，不用一种？ | 关键词擅长精确匹配但不认识同义词；向量懂语义但对精确字符串不敏感，还可能找出意思相近却无关的内容。两个一起用再融合排序，比任何单独一种都稳。 |
| 两路结果怎么合并？ | 用 RRF，只看名次不看分数。因为 BM25 和余弦相似度量纲不同，直接加权要先归一化，而归一化要调参；RRF 天然免疫这个问题。 |
| 分块为什么这么切？ | 结构优先：先按标题层级和段落切，保证一块只讲一件事；再用长度兜底、块间留重叠，避免答案正好被切在边界上。切太大主题混杂会引入噪音，切太小上下文不足，模型看不懂。 |
| 怎么防止模型胡编？ | 两层：提示词里硬性要求只依据资料作答、没有依据就直说；检索不到任何片段时干脆不调用模型，直接返回固定回答。 |
| 首字延迟是多少？怎么优化？ | 实测 801 毫秒。做法是 SSE 流式返回，模型生成一段就推一段，用户不用等整段完成。 |
| 模型服务挂了怎么办？ | 配置了降级顺序，主模型失败自动切备用。有个边界：流式只有在还没吐出第一个字时才能切，否则用户会看到两段拼接的内容。实测把主模型地址改成不通的端口，请求仍然正常返回。 |
| 成本怎么控制？ | 每次调用都记 token 和金额（失败的也记），按模型汇总，接口是 `/api/usage/summary`。实测一次提问约 387 + 126 token、0.0018 元。 |
| 你怎么证明混合检索有用？ | 我建了 12 道题的评测集，跑出来在这个集子上混合并没有赢过关键词——因为我的题目措辞和文档用词重合，对关键词有利。这个结论比"混合更好"更有价值：它说明评测集本身也会骗人。 |
| 为什么不动手调参数？ | 我调了，而且数据告诉我不能调：RRF 融合分对相关和不相关的问题几乎一样（0.033 对 0.028），结构上就不能用来做阈值。能做阈值的是 BM25 分数（4.68 对 1.00），我按这个实现了门控，但默认关闭，因为 12 道题标出来的数字不够当默认值。 |
| 系统扛得住多大压力？ | 我要诚实说：目前是单机实现，会话存在内存里，索引是本地文件。真要多实例、要高可用，会话得挪到 Redis，索引要么做共享存储要么拆成独立检索服务。（主动说出边界，比被问出来强） |
| 你觉得哪里做得不够好？ | 三处：一是向量用的还是本地兜底实现，没有真正的语义能力，接上真实向量模型后要重建索引；二是相关性没有阈值门控，不相关的问题也会检索出片段，只能靠提示词拦住；三是解析期间事务占着数据库连接，量大了要拆成三段短事务。 |

## 六、自测：这五个问题你能答上来吗

答不上来的就是我们今天要补的地方。

1. 用户问一句话之后，系统内部依次发生了哪几件事？
2. "两个工人"分别擅长什么、各有什么短板？为什么要把他们的结果合并？
3. 为什么答案里会带 `[1]` `[2]` 这种编号，它和接口返回的哪个字段对应？
4. 如果我把分块大小从 800 改成 2000，会发生什么？为什么不能随便改？
5. 这个系统现在有哪些明显的不足？如果要上线给全公司用，你会先改哪三件事？

## 七、现在还不完美的地方（以及为什么先不动）

这一节是故意留的。**能说清楚自己的系统哪里不行，比宣称它完美更有说服力。**

| 不足 | 为什么现在不动 |
| --- | --- |
| 向量用的是本地兜底实现（字符哈希），没有真正的语义能力 | 需要另外申请一个向量模型的密钥，链路已经预留好接口，改配置 + 重建索引即可 |
| 检索没有相关性阈值门控 | 阈值必须用评测集标定，凭感觉设一个数字只会引入新的不确定性，等 M5 用数据说话 |
| 会话存在单机内存，重启即丢 | 单机演示够用；正式做法是放 Redis，但现在引入它只是增加复杂度 |
| 解析期间数据库连接被长时间占用 | 当前文档量小，不是瓶颈；量大之后拆成三段短事务即可 |
| 没有前端界面 | 现在用命令行验证，界面对理解系统没有帮助；等核心链路稳定再做 |
